# 测试规范

## 变更分级与验证策略

开始验证前，应先根据实际影响范围判断变更等级。验证范围以足以证明本次改动正确为准，不因改动简单而省略验证，也不对低风险改动默认执行完整检查。

## 执行效率与时间控制

开始修改前先声明本次采用轻量变更、中等变更或完整检查。未命中升级条件时，必须使用与风险匹配的最低验证等级。

- 浏览器等待应使用明确的目标元素和合理的短超时，不使用长时间固定等待；首次验证失败后先判断是产品问题、测试桩问题还是环境问题。
- 模拟接口只覆盖当前目标流程；简单样式问题优先复用现有页面状态，不为验证搭建复杂数据链路。
- 相同命令或相同浏览器流程不得在没有代码变化时重复执行。
- 能并行执行的只读检索和独立检查应并行执行；依赖前一步结果的操作保持串行。
- 轻量流程失败时只补充与失败原因直接相关的检查；确认影响范围扩大后再升级到标准或完整流程。
- 工具或环境阻塞超过预期时，应尽快说明阻塞点并采用更小的可验证方案，不让一次局部调整停留在无效等待中。

### 快速迭代模式

当需求中出现“先看效果”“粗版”“初版”“快速调整”“样式再调一下”“我先看看”等表达，或页面仍处于连续视觉和交互试调阶段时，默认进入快速迭代模式。开发阶段判断优先于常规变更分级，避免对尚未定稿的页面重复执行完整验收。

- 修改后只刷新并验证当前目标页面、当前操作或当前视口。
- 确认页面能够渲染、目标改动生效且没有明显运行时错误即可交付查看。
- 不默认执行 `npm run check`、生产构建、全量测试、完整端到端流程或桌面与移动端双重截图。
- 不为每轮小调整重复创建临时浏览器脚本；优先复用现有页面、热更新和固定冒烟检查。
- 连续反馈中的文案、间距、颜色、显隐和局部交互应合并处理，在页面结构确认后统一验证。
- 若用户明确要求“定稿”“完整检查”“准备提交”“准备部署”或“验收”，退出快速迭代模式并执行对应的完整检查。

快速迭代不适用于接口协议、权限、安全、真实数据写入、数据删除、持久化结构和构建配置变更；这些变更仍按风险等级执行必要检查。

### 局部调整的时间与范围控制

- 文案、显隐、选项和样式等局部调整，以1–3分钟完成修改和目标验证为执行目标，不作为跳过必要验证的硬性时限。
- 修改前先判断是否实际影响接口或持久化。移除展示入口不等于需要删除数据库字段；能保留兼容的数据不顺带清理，不因“顺便检查后端”扩大到无关模块。
- 将同轮调整集中修改，复用已有页面和测试环境，一次完成目标检查。测试通过后，只有新增改动、失败或未解决风险才补充检查，不重复运行已经充分的验证。
- 局部新增确认、冷却等交互，只运行对应测试及必要静态检查；不因新增一个按钮自动升级为全量检查。真正涉及接口、权限或数据写入规则时，仍按风险执行必要验证。
- 测试脚本或浏览器定位出错时，先识别为验证工具问题还是产品问题，仅修复相关部分，不反复切换工具或扩展验证链路。
- 预计明显超过1–3分钟，或发现必须扩大改动范围时，及时说明具体原因、已完成部分和剩余工作；已授权且必要的工作继续完成，不为常规可逆调整额外等待确认。
- 不将“节省时间”作为宣称未执行测试通过、忽略数据风险或隐瞒验证缺口的理由。交付时简要说明实际检查及未覆盖内容。

### 轻量变更

适用于文案、颜色、间距、图标、显隐、局部定位、菜单或浮层展示问题，以及不改变业务状态的简单路由调整；目标是在通常 1～3 分钟内完成一次调整和验证。

1. 只在目标组件、直接关联样式和必要调用方中精准搜索，不扫描 `node_modules`，不读取与问题无关的大型文件。
2. 进行最小范围修改，不顺带重构或整理无关代码；涉及文案、入口或路径时确认没有应同步修改的残留。
3. 执行受影响文件对应的类型检查或最小静态检查；纯样式修改可以直接进入目标页面验证。
4. 复用正在运行的开发服务器和当前页面数据，在真实浏览器中只验证一个目标视口和一个目标交互。
5. 只在改动涉及响应式样式时补充移动端验证。
6. 目标效果正确且没有相关运行时错误后立即停止，不追加 `npm run check`、生产构建、重复截图或无关页面检查。

### 中等变更

适用于组件交互、表单校验、局部状态处理、接口字段映射和单一业务流程调整。

- 执行 `npm run typecheck` 和 `npm run lint`。
- 执行受影响模块的相关测试；没有相关测试时，应补充必要测试或记录测试缺口。
- 使用真实浏览器验证目标操作流程，并检查控制台错误。
- 涉及布局、抽屉、弹窗或日期面板时，同时验证桌面端和移动端。

### 完整检查

适用于公共组件、全局状态、接口协议、构建配置、权限、安全、数据持久化和核心业务流程变更。

- 执行 `npm run check`，覆盖类型检查、代码规范、自动化测试和生产构建。
- 使用真实浏览器完成受影响核心流程的端到端验证。
- 同时验证桌面端和移动端，并检查页面控制台和网络请求。
- 涉及后端或数据库时，验证前端操作、接口响应、数据保存和结果回显的完整链路。

### 验证升级条件

出现以下任一情况时，验证等级至少上调一级；已属于中等变更且命中高风险项时，升级为完整检查：

- 搜索发现旧入口、旧路由或关联文案仍有残留。
- 修改影响公共组件、跨页面状态或多个业务模块。
- 实际影响范围超过最初判断，或行为边界无法明确确认。
- 类型检查、代码规范检查、自动化测试或浏览器验证失败。
- 任何阶段涉及接口协议、权限、安全、真实数据写入、数据删除、持久化结构或构建配置；或者在非快速迭代阶段修改核心工作流。

验证完成后，应在交付说明中简要说明采用的验证等级、已执行的检查以及未覆盖的风险。

## 连续页面迭代节奏

页面从粗版到定稿时，按以下节奏执行：

1. 粗版实现：完成目标结构和主要交互，只验证目标页面可用。
2. 连续调整：根据反馈快速修改，不在每轮重复全量检查。
3. 结构确认：统一执行类型检查、代码规范检查和目标流程验证。
4. 阶段定稿：执行 `npm run check`、桌面与移动端验证及必要的完整业务链路检查。

同一轮调整如包含多个细小问题，应集中修改、集中刷新和集中反馈，避免为单个文案或间距分别启动一套验证流程。

## 测试分层

- Vitest：纯函数、类型边界和业务状态转换。
- React Testing Library：按用户可见行为测试组件，不验证内部实现细节。
- Playwright：验证需求填写、AI 描述、拆解工作项、编辑工作项和发布任务等关键流程。
- 完整验证：前端操作需要覆盖后端接口、数据库保存和结果回显。

## 必测场景

- API 成功、业务失败、非 JSON 错误和响应结构不合法。
- 异步任务从 QUEUED、PROCESSING 到 SUCCESS/FAILED。
- 路由刷新和浏览器返回。
- 工作项树展开、选择、编辑、删除和新增。
- 抽屉、弹窗、日期面板在桌面与移动视口中的位置。
- 无内容、加载中、失败和重试状态。

测试优先查询用户可见的文本、标签和角色，仅在没有合理语义选择器时使用 `data-testid`。
