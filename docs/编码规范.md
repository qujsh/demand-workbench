# 编码规范

## TypeScript

- 新文件使用 `.ts` 或 `.tsx`。
- 接口响应、领域对象和组件 Props 必须有明确类型。
- 不使用 `any` 绕过正常建模；对第三方或历史数据可在边界处校验后转换。
- 固定范围字段使用联合类型，例如工作项类型、状态和优先级。
- 不在组件中散落字符串状态判断，优先封装为类型、映射或业务函数。

## React

- 组件只负责展示和组合；API、轮询、缓存放入功能 Hook。
- 不在 Effect 中派生可以直接计算的状态。
- 列表项使用稳定业务 ID，不使用数组下标作为可变列表的 Key。
- 复杂页面状态优先使用 `useReducer`；服务端状态不放入 Context 或 Reducer。
- Effect 必须清理监听器、计时器和外部订阅。
- 交互按钮必须提供清晰文本或 `aria-label`。

## 输入与渲染性能

- 受控输入框的高频状态应保留在最小必要组件内，确保输入值可以立即回显。
- 不得在每次按键时同步更新会触发整页、大型列表、树或图表重新渲染的父级状态；根据业务需要使用失焦保存、防抖或 React 低优先级更新。
- 输入状态和持久化状态应分开：输入负责即时反馈，保存或同步负责数据一致性，不让网络请求或大范围状态更新阻塞键盘事件。
- CSS 的 `display: none`、`visibility: hidden` 等只影响显示，不会阻止 React 计算和渲染。隐藏的昂贵区域应使用条件渲染、组件拆分或稳定的渲染边界。
- 工作项树、大型表格、甘特图等高成本组件应使用 `memo` 或等价隔离方式，并保持传入对象、数组和回调引用稳定，避免被无关输入状态触发。
- 不把大型树或列表与频繁变化的输入草稿放在同一个不可隔离的渲染组件内；必要时拆分输入编辑器、标题区域和数据视图。
- `useMemo`、`useCallback`、`useDeferredValue` 和 `startTransition` 只在能够缩小实际渲染范围或降低输入阻塞时使用，不作为无证据的默认优化。

### 输入性能验证

1. 使用真实浏览器连续输入和删除，确认文字逐字即时显示，光标位置稳定。
2. 同时覆盖单行输入框和受影响的多行文本框；存在抽屉、弹窗或树内编辑时验证相应编辑器。
3. 检查输入期间是否出现超过 50ms 的主线程长任务，以及是否触发无关接口请求、iframe 重载或大型组件重复渲染。
4. 页面包含第三方 iframe 时，应在性能验证中阻止或隔离其加载，避免把第三方脚本开销误判为本项目输入性能。
5. 性能结论应描述交互是否流畅、是否存在长任务和渲染范围，不把单次机器环境下的耗时记录为固定验收标准。

## 文件与命名

- 组件和页面使用 PascalCase。
- Hook 使用 `useXxx`。
- 接口模块使用 `xxxApi.ts`，Schema 使用 `xxxSchemas.ts`。
- 每个文件承担一个主要职责；超过约 250 行时应检查是否存在可拆分职责，不机械按行数拆分。

## 质量命令

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run check
```

## 缺陷修复效率规范

小范围功能缺陷默认采用“定位断点、最小修改、定向验证、及时停止”的流程。除非影响范围扩大，不得把局部修复自动升级为重复的全量检查。

### 推荐流程

1. 用一次代码检索确认用户操作、前端状态、接口和持久化之间的断点；已有接口可以满足需求时，不新增重复接口。
2. 只修改直接关联的 Hook、API 映射或组件调用，不顺带重构无关代码。
3. 优先运行受影响模块的定向测试；测试通过后，根据变更等级选择一次类型检查或一次 `npm run check`，不得在没有代码变化时重复执行相同检查。
4. 浏览器只验证一条目标路径，例如“打开页面 -> 刷新 -> 执行目标操作 -> 检查结果回显”。
5. 使用明确的目标文本、元素状态或接口响应作为证据。能够通过局部 DOM 断言证明结果时，不采集完整页面 DOM、无关 iframe 内容或重复截图。
6. 目标交互、相关控制台状态和必要静态检查均通过后立即停止；仅在发现跨模块影响、协议变化或持久化风险时扩大验证范围。

### 避免重复工作

- 不先运行完整类型、Lint 和测试，再无代码变化地重复运行包含相同步骤的 `npm run check`。
- 懒加载页面应先等待目标元素出现，再采集一次有效快照，避免因页面尚未完成渲染而重复检查。
- 页面包含第三方 iframe 时，只检查本项目页面区域和相关控制台错误，不展开或记录第三方 iframe 的完整 DOM。
- 功能正确性已有文本或状态断言证明时，截图仅用于视觉问题或用户明确需要查看效果的场景。
- 后端接口已经通过代码和真实响应确认可用时，不为同一结论重复查询数据库、日志和接口。

### 时间目标

对于单一状态恢复、字段映射或局部交互缺陷，通常应在 3～4 分钟内完成定位、修改和定向验证。时间目标不覆盖接口协议、权限、安全、真实数据写入、数据删除、持久化结构或其他需要完整检查的高风险变更。

## 全栈持久化功能效率规范

涉及前端交互、后端接口和数据库写入的功能，必须验证完整数据链路，但应避免把接口验证、页面验证和完整检查拆成多轮重复流程。通常应在 8～12 分钟内完成实现和验证。

### 实施顺序

1. 一次性确认现有前端入口、API、应用服务、Repository、Mapper 和表结构，明确缺失边界后再编辑。
2. 前端和后端分别使用小范围补丁；修改长文件前先读取准确上下文，避免因上下文不匹配导致整批修改失败。
3. 后端先执行编译和受影响服务、Controller 的定向测试；前端执行类型检查和受影响 API、Hook 的定向测试。
4. 定向检查通过后，只启动一组临时验证服务，并记录实际端口，避免与开发者正在运行的 IDE 服务冲突。
5. 使用一条自动化业务路径完成“操作 -> 保存 -> 刷新或重新查询 -> 回显 -> 清理测试数据”，不得为同一结论分别进行多轮手工接口验证和页面验证。
6. 最终按高风险变更要求执行一次前端 `npm run check` 和一次后端完整测试；没有代码变化时不重复执行。
7. 验证结束后立即关闭临时服务，并确认临时数据已删除或回滚。

### 浏览器验证约束

- 优先使用稳定的角色、标签和目标文本定位元素，单个脚本连续完成目标流程，减少工具往返。
- 只采集目标业务区域和必要状态，不输出完整页面 DOM。
- 页面包含豆包等第三方 iframe 时，应在测试中阻止其加载或排除其 DOM、网络和控制台信息；第三方内容不属于目标流程时不得等待其完成。
- 首次快照必须等待目标元素出现后再采集；同一页面状态不得重复生成快照。
- 功能验证以保存结果、刷新回显和接口响应为主要证据；非视觉问题不额外截图。
- 单个浏览器操作出现超时后应立即检查定位方式，不使用相同条件重复等待。

### 测试数据与服务

- 端到端验证使用带有明确测试标识的临时数据，并在同一自动化流程的 `finally` 或等价清理阶段删除。
- 可以通过一次页面操作证明前端到数据库完整链路时，不再额外执行内容相同的手工写入请求。
- 临时后端和前端应并行启动；健康检查通过后立即开始验证，不以固定时长等待。
- 不终止开发者通过 IDE 或其他终端启动的进程；需要新版服务时使用独立端口，验证完成后只关闭本次创建的进程。

### 时间控制

- 定位与方案确认：约 2 分钟。
- 前后端实现：约 4～5 分钟。
- 定向检查：约 1 分钟。
- 单次端到端验证与数据清理：约 2 分钟。
- 完整检查：按实际测试耗时执行，通常不应重复。

如果超过 12 分钟，应在继续前判断耗时来自产品缺陷、环境阻塞、测试等待还是工具输出过大，并立即缩小到最小可验证路径。完整测试本身的必要运行时间不计为无效耗时，但不得让空闲的临时服务运行时间替代有效验证进度。
