# 协议版本与登录确认（2026-11-14）

## 使用流程

1. 手动重启共享后端，Flyway执行 `V202611140100__legal_protocols.sql`。本轮未重启用户服务、未向开发库导入测试协议。
2. 管理员进入B端“系统配置 → 协议管理”（`/system/legal`）。新权限为 `legal.manage`，迁移只授予内置管理员；其他角色需单独授权。
3. 选择用户协议或隐私政策，上传UTF-8 HTML（最大1MB）创建草稿。无需Word、手填版本、生效日期或更新说明；日期和说明由HTML正文携带。
4. 对照法务原稿校对服务端清理后的桌面／手机预览，确认发布。两类协议分别从V1递增，正式发布时才编号，重复发布同稿不增加版本。
5. 两份协议均正式发布后，C端主动密码／短信登录需要明确勾选。缺少协议时登录失败关闭，不回退虚假协议或绕过确认；匿名公开浏览继续可用。

## 上传与不可变性

仅保留安全正文标签、标题、段落、列表、表格和受限链接。原始HTML保存在数据库供内部留档，不直接执行或返回；脚本、事件、外部样式、图片、本机路径和iframe等嵌入内容被清理。法务文件如使用图片承载重要条款，需要先改为文字，不能直接按原样发布。

清理后的实际展示HTML保存完整快照与SHA-256摘要。B/C端均以sandbox iframe和CSP隔离正文，不执行脚本，当前隔离阅读器不开放外链弹窗。统一排版可能改变Word导出样式，发布前必须人工校对；不会自动解析正文日期或定时生效，点击发布立即切换当前版本。

已发布正文不允许更新或删除，新内容创建新草稿；旧版仍可按固定地址回看。草稿有乐观修订号；基于旧正式版创建的落后草稿不能覆盖后来发布版本，需重新上传创建草稿。类型行锁和数据库唯一索引保证并发版本唯一。

## 登录证据边界

C端使用独立 `POST /api/v1/c/legal/login`，提交手机号、凭据、登录方式、accepted和两份快照编号；用户身份只能由认证取得，接受时间由数据库产生。后端在事务内锁定两份当前版本，版本过期先返回409/LEGAL_CHANGED，不消费验证码、不创建会话；前端刷新协议并取消勾选，要求再次阅读确认。

认证成功后，会话与接受记录原子提交；保存失败回滚新会话。每次主动成功登录追加事件编号、用户、两份快照、登录方式、入口、服务端时间及会话令牌摘要，不存明文密码、验证码或会话令牌。登录失败不生成同意记录；刷新页面／恢复Cookie会话不伪造再次同意。SHA-256仅用于核对内容，不等于可信时间戳或不可篡改审计系统。

既有B端共享认证接口保持兼容，不强制套用C端协议，也不补造历史B端登录的接受记录。记录的是C端主动登录确认，不表示所有既有账号都已接受当前版本。

C端页面：`/legal/terms`、`/legal/privacy`为当前版本入口；`/legal/terms/数字版本`、`/legal/privacy/数字版本`为固定版本页面。登录弹窗链接固定为本次要求接受的版本，新页打开保留登录输入。页脚也有公开入口。

B端“用户同意记录”支持用户编号精确筛选、50条游标分页及点击版本查看当时正文；不返回手机号、凭据或令牌摘要。草稿和发布内部资料均不通过C端接口公开。
