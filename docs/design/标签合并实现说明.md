# 标签合并实现说明

## 页面交互

管理标签顶部保留统一“合并”入口，位于“添加”后。进入后，输入框和添加按钮切换为方向预览、确认合并和取消，标签前的手柄切换为复选框。最多选择两个标签，按“先选 → 后选”执行，分别标记为“来源”和“保留”；此时不可排序或删除。

提交只负责创建后台任务，不等待记录全部处理完毕。管理面板切换为任务状态、合并方向、百分比、已处理/总记录数。排队和准备阶段显示对应状态，收尾校验完成后才显示100%。关闭面板不影响处理，刷新页面可恢复进度；右侧管理入口旁显示排队、合并进度或待重试状态。

处理失败展示重试入口，保留已提交的进度并继续锁定标签。重试从断点继续，不重复已提交批次。暂不提供取消或一键拆分，以免部分完成时产生不一致状态。

完成后自动刷新标签、记录与计数；正在按来源标签浏览时切换为目标标签。目标排序保持原位。

## 标签使用限制

从提交成功起至完成（包括排队和失败待重试），当前用户不能新增、删除、排序或再次合并标签，也不能在正文中添加或移除标签。编辑器禁用标签入口和候选，富文本事务拦截手工输入、粘贴等标签变更。正常正文、图片和其他字段仍可编辑，新增无标签记录仍被允许。

后端在用户标签顺序行锁内重复校验，旧页面、其他标签页或直接接口调用不能绕过限制。正文保存允许合并前后等价的标签集合，但拒绝真实增删；批处理会递增记录和草稿版本，旧编辑器可能收到版本冲突，需重新加载后保存。

普通已删除标签不得重新使用或自动恢复。合并来源保留历史名称映射，旧正文中的来源名称解析至有效目标，不重新生成来源标签；目标后来被删除时同样拒绝使用。

## 接口

| 方法 | 地址                                                    | 说明                                            |
| ---- | ------------------------------------------------------- | ----------------------------------------------- |
| POST | `/api/v1/shares/tags/merge?sourceTagNo=…&targetTagNo=…` | JSON `{ "expectedOrderVersion": 12 }`，返回任务 |
| GET  | `/api/v1/shares/tags/merge-task`                        | 返回 `{ "task": 任务或null }`，仅限本人最近任务 |
| POST | `/api/v1/shares/tags/merge-task/retry?taskNo=…`         | JSON `{}`，失败任务重新排队，返回原任务及断点   |

任务业务数据示例（外层沿用success/msg/errorCode/errorMsg）：

```json
{
  "taskNo": "MERGE-…",
  "sourceTagNo": "TAG-source",
  "targetTagNo": "TAG-target",
  "sourceName": "拍摄",
  "targetName": "摄影",
  "status": "RUNNING",
  "totalCount": 1000,
  "processedCount": 300,
  "progress": 30,
  "errorMsg": null
}
```

状态：`QUEUED → PREPARING → RUNNING → FINALIZING → COMPLETED`。异常转为`FAILED`，重试回到`QUEUED`。版本冲突或标签锁定返回409；标签锁定错误码为`S048107005`；跨用户任务和无效标签返回404。

TanStack Query统一管理查询，活动任务每秒查询一次，页面在后台时暂停轮询；完成或失败时停止轮询。重试提交后恢复轮询。没有组件自行创建重复定时器。

## 数据和事务

Flyway `V202611042200__share_tag_merge_jobs.sql` 新增：

- `share_tag_merge_job`：所属用户、来源/目标快照、状态、总量、已处理量、游标、租约令牌和到期时间、重试信息。
- `share_tag_merge_item`：按任务和记录去重的稳定工作清单。
- `share_tag_merge_control`：数据库唯一控制行，统一分配全系统执行名额。
- `share_tag_order.merge_task_no`：当前用户未结束任务，也是所有标签写入的业务锁。

提交事务只锁定用户标签、验证版本并创建任务。准备阶段建立来源正式记录（含回收站）及编辑草稿的去重工作清单；每批默认100条，通过清单主键游标读取。单批记录/草稿快照、关系投影、版本和任务游标在同一事务提交，异常整批回滚。

合并只更新标签及相关版本，不重写附件、媒体登记、引用或时间线位置。原文保留，来源和目标在同一记录出现时去重。只在草稿中出现来源的记录同样进入清单。

允许正文保存时提前完成等价标签替换，因此准备阶段统计的是当时仍待处理的去重清单；`processedCount`表示已扫描提交的清单记录数。准备完成后总数固定，不按标签计数简单相加。

收尾验证来源关系和草稿已无遗留，再软删除来源、压平历史名称映射、递增标签顺序版本并解除用户标签锁。处理期间来源/目标标签筛选查询二者并集，避免分批过程中记录从筛选列表消失。

## 并发和恢复配置

默认全系统最多执行2个合并任务，每个实例最多4个工作线程，多余任务排队。同一用户最多保留一个未完成任务。全系统配额通过MySQL控制行锁实现，多实例也共享同一上限，不能仅用JVM线程数作为全局限制。

`share.tag-merge.max-concurrent`默认2，**只初始化数据库控制行**；之后数据库中的`share_tag_merge_control.max_concurrent`是唯一生效值，避免不同实例覆盖配置。开发时可通过以下语句统一调整，建议范围1–32；调低不强制中断已运行任务，名额自然释放后遵守新上限：

```sql
UPDATE share_tag_merge_control SET max_concurrent = 2 WHERE id = 1 AND deleted = 0;
```

`share.tag-merge.batch-size`默认100（范围1–500），`share.tag-merge.poll-delay-ms`默认1000，`share.tag-merge.worker-enabled`默认true。无需额外部署消息队列。

执行租约120秒，每批提交时续期；宕机后由其他实例或重启后的工作线程接管过期任务。执行令牌阻止旧工作线程继续提交或把新执行者标记为失败。数据库持久化进度不依赖浏览器。

当前保留已完成任务与工作清单，尚无自动清理任务；后续可单独制定保留时长。1000条集成测试验证正确性，不作为30万条合并耗时或生产吞吐承诺。
